# 词包项目与 cdict 迁移规划

修订：2026-10-27。根据用户纠正，本版取代先前将 MediaWiki 采集和 cdict 转换捆绑为通用工具项目的方案。**本次只更新规划与交付文档，不修改 miancak、不开发工具、不抓取数据、不创建仓库。**

## 1. 仓库边界与数量

不建立 `rime-lexicon-packs` 通用仓库，也不预设必须新建 `rime-lexicon-tools`。先复用现有开源工具和已有词表，只有需要我们长期维护额外词包时，再为该具体词包建立仓库。

因此不固定“现在建一个工具、以后再建一个 packs”的数量。可以暂时没有新增仓库；随后按独立维护／发布的词源或主题建词包项目，不按每个词表文件拆一个仓库。名称可用 `rime-<具体词源或主题>-dict`，只是命名示例，当前没有选定站点、发布范围或实际仓库名。

cdict 共同源格式与后端迁移是另一条研究路线，沿用 [#18](https://github.com/AuroraLilja8514/miancak/issues/18) 和 [D1–D4](DICTIONARY_ROADMAP.md)。是否需要独立仓库、fork 或小型适配模块，完成现有工具与数据映射评估后再决定；不自动塞进 MediaWiki 词包项目。

## 2. 先复用的开源能力

2026-10-27 核对了以下项目的原始 README；这是候选能力核对，不是安装／运行、依赖审计或 miancak 兼容验收。

| 项目 | README 已说明的能力 | 对本规划的用途 |
| --- | --- | --- |
| [outloudvi/mw2fcitx](https://github.com/outloudvi/mw2fcitx) | 从 MediaWiki 构建 fcitx5／Rime 词库；可读 API 或本地标题文件；具有可配置处理、拼音转换及内置 Rime 生成器 | 作为自选 MediaWiki 词源的优先评估工具；先写站点配置／修正规则和验证，不重新实现通用抓取与生成器 |
| [felixonmars/fcitx5-pinyin-zhwiki](https://github.com/felixonmars/fcitx5-pinyin-zhwiki) | 提供中文维基百科词库，并说明 Rime 安装与构建方式 | 如目标是现有中文维基百科词库，先评估直接采用其 Rime 数据／构建流程，避免重复维护相同数据 |

复用顺序：已有兼容词表 → 固定版本的上游工具及配置 → 必要的薄适配 → 确认上游不能满足的缺口再实现。仅在确需维护补丁时评估 fork，不为改变项目名复制整套工具。依赖版本／commit、输入快照、配置和必要的修正规则都需固定。

工具支持 Rime 不代表输出已通过 miancak 当前导入门禁。实施时逐项核对 [现有格式](RIME_WORD_TABLES.md)：文件扩展名和表头、Tab 数据列、明确的无调拼音、ü／v、权重、依赖、大小与条目上限。只对确认的差异作可追溯适配；不静默丢弃带调、未编码或无法确定读音的数据。

两个项目的说明都区分工具代码与生成词库的数据许可。采用时分别保存上游代码许可和具体词源的许可／署名，不根据工具许可证推断词库的分发条件。本轮尚未选定、下载或重新分发任何词表。

## 3. 具体词包仓库应该放什么

一个具体词包项目围绕“我们要额外维护什么词汇”建立，可以同时产出该词源的多个词表，不承担通用转换平台或 Android 输入法职责。

- README：目标词源／主题、收录范围、适用输入码、用途和已知限制。
- 固定的上游工具版本、词源快照／修订及获取方式。
- 站点配置、过滤／去重规则、读音修正表和必要的小型适配。
- 可重复构建的入口、有限超时、合成测试样本与校验报告。
- 来源、许可、署名、修改记录、输出哈希和发布说明。
- 实际发布所需的 Rime 兼容源词表；大体积原始快照／生成结果是否放 Git 或 Releases，按该词包决定，不预先建立统一 packs 仓库。

所有受维护的脚本提供可配置有限总超时，默认可用 3600 秒；网络步骤另设有限超时、重试和速率。具体抓取站点、范围与频率在该词包立项时确定。本次不设置在线抓取任务或发布流程。

优先作为附加词表，不自动替换 miancak 当前默认词包。生成流程应保留原始来源和修正规则，读音错误可追溯；词频的采用／调整需说明，不能以词条数量替代日用质量。

## 4. 词包路线：不等待 cdict

| 顺序 | 工作 | 验收 |
| --- | --- | --- |
| V0 | 确定具体词源与已有成果 | 明确是直接采用现成 Rime 词表，还是使用现有工具生成额外内容；来源与许可明确。若上游已满足需求，无须新建仓库 |
| V1 | 用固定版本工具做小样 | 使用已允许的小样本／本地标题输入验证配置、读音修正与 Rime 输出；记录与当前导入格式的差异，不先开发通用工具 |
| V2 | 有独立维护需求时建具体词包仓库 | 保存配置、版本、修正规则、来源及测试；固定输入重复产出相同词表字节，异常／缺依赖／超时不覆盖可用结果 |
| V3 | 实际应用验收与发布 | 通过正常文件选择导入，启用附加表后检查实际候选／正文、排序、重启、学习保留和失败恢复；通过后才声明该词包可用于对应应用版本 |

这条路线不以“先完成英语 cdict 转换”或“先写共同工具平台”为前置。当前只完成候选 README 核对与规划修订，未完成 V1–V3，也未创建具体词包仓库。

## 5. cdict 路线：单独评估

1. 清点 cdict 的可追溯源词表、运行时格式、权重／元数据和已有转换工具。
2. 明确要解决的是源词表复用、Rime 源格式输出，还是运行时／补全／纠错行为迁移；它们需要分别验收。
3. 用一个语言小样验证映射、大小写／重音／频率保留、重复处理与不支持字段。
4. 再决定最合适的代码归属：复用上游、适配模块、fork 或独立项目。当前不固定仓库数和名称。

不能把二进制改名视为转换完成，也不能根据生成词表成功宣称候选／纠错等价。共同源格式的长期目标保留；是否更换某个语言后端由 miancak 的实际输入验收决定。

## 6. miancak 继续负责的部分

应用保留布局／Fn／Shift、候选、输入连接、个人学习、词表选择／附加开关、正常导入、离线部署、回滚和升级。用户可以直接使用已有兼容词表，无需先安装我们的工具或完整第三方方案。

具体词包项目生产数据；应用对真实输入行为负责。新增 profile 或语言算法需单独集成和验收，不能由词包仓库自行宣称支持。主应用 N1–N4 与质量／交付计划不等待词包或 cdict 路线；H1 仍后置讨论，Compose 保持现状。
